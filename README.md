# 💧 AquaGuard

AquaGuard is an AI-powered water conservation platform: a chatbot with persistent
conversation history, an interactive water-footprint quiz, a leak cost calculator,
a global water-scarcity dashboard, and a footprint leaderboard — built as a React
single-page app backed by a small Flask API and Firebase.

## Motivation

Freshwater is finite, unevenly distributed, and under increasing pressure from
population growth, climate change, and inefficient use. Most people know water
conservation "matters" in the abstract, but lack three things that turn awareness
into action: an easy way to ask specific questions and get a specific answer, a
concrete sense of *their own* usage relative to a benchmark, and visibility into
why the issue is urgent beyond their own household. AquaGuard's chatbot,
footprint quiz, and cost calculator address the first two; the global scarcity
dashboard addresses the third — grounding an individual's habits in the broader
picture of who actually has abundant water and who doesn't.

## Objectives

- Provide instant, on-topic conservation guidance through a conversational AI
  interface that understands and responds in the user's own language.
- Let a user estimate their personal daily water footprint from a short quiz and
  see concrete, ranked suggestions for where to improve.
- Translate abstract habits like "a dripping faucet" into a concrete number:
  gallons wasted per year and the dollar cost, so the impact is tangible.
- Contextualize personal water use against real disparities in global water
  availability, so conservation reads as more than a personal chore.
- Encourage sustained engagement through a leaderboard, rather than a one-time
  read of a tips page.

## Scope

**In scope (implemented):** an authenticated multi-user web application with a
scoped AI chat assistant, persistent chat history, a scored self-assessment quiz,
a standalone cost calculator, a static-but-rich global comparison dashboard, and a
leaderboard tying the quiz back into a shared, competitive context.

**Out of scope (possible future work):** live integration with a household's
actual smart-meter or utility-bill data (the calculator and quiz use self-reported
inputs, not sensor data); push/email notifications for conservation reminders;
a native mobile app (the current app is a responsive web SPA); and live, API-fed
regional water-scarcity data rather than the current curated dataset.

## Features

- **AI Chat Assistant** — ask natural-language questions about saving water; answers
  are generated by Google's Gemini model, scoped to water-related topics only and
  tuned for short, conversational replies. Language is auto-detected so the same
  assistant works in the user's own language, not just English. Conversations are
  saved per-user in Firestore (ChatGPT-style history sidebar, "New Chat", delete),
  so nothing is lost when you navigate to another page, and the UI still works
  immediately even if the background save hasn't completed yet.
- **Water Footprint Quiz** — a short interactive quiz about daily habits (showers,
  laundry, dishes, leaks, lawn watering, diet) that estimates your daily water
  footprint in gallons, compares it to the US average, and gives targeted
  improvement tips based specifically on your highest-impact answers. Optionally
  save your score to the leaderboard.
- **Leak & Waste Cost Calculator** — an interactive calculator that turns a
  household leak or habit into gallons wasted per day/year and an annual dollar
  cost, with relatable comparisons (swimming pools, showers) so the number means
  something.
- **Global Water Scarcity Dashboard** — renewable water resources per capita and
  water-stress levels across ten countries, with a log-scale comparison chart and
  per-region facts, to give personal conservation a global frame of reference.
- **Leaderboard** — ranks users by quiz footprint score (lowest wins), turning a
  one-off self-assessment into an ongoing, shared incentive.
- **Authentication** — email/password (with forgot-password reset) and Google
  sign-in via Firebase Auth, with a single shared auth session (no re-check
  flicker or redirect when navigating between pages).

## Architecture

```
React SPA (src/)  ──HTTP──▶  Flask API (backend/app.py)  ──▶  Gemini API
      │
      └──────────────────▶  Firebase Auth + Firestore
```

The React app handles routing, auth, and the quiz/calculator/dashboard/leaderboard
UI directly against Firebase. Chat messages are sent to the Flask backend, which
detects the message's language (with a confidence and length floor so short
English phrases aren't mistaken for another language), translates non-English
input to English, asks Gemini (scoped to water topics, tuned for concise replies)
for a response, and translates the reply back before returning it. Each chat
exchange is persisted to the active conversation document in Firestore.

## Setup

### Prerequisites

- Node.js 18+ and npm
- Python 3.10+
- A [Firebase](https://console.firebase.google.com/) project with **Authentication**
  (Email/Password + Google providers enabled) and **Firestore** turned on
- A [Gemini API key](https://aistudio.google.com/app/apikey)

### 1. Frontend

```bash
npm install
cp .env.example .env
```

Fill in `.env` with your Firebase project's web config (Firebase Console →
Project Settings → General → Your apps → Web app):

```
REACT_APP_FIREBASE_API_KEY=...
REACT_APP_FIREBASE_AUTH_DOMAIN=...
REACT_APP_FIREBASE_PROJECT_ID=...
REACT_APP_FIREBASE_STORAGE_BUCKET=...
REACT_APP_FIREBASE_MESSAGING_SENDER_ID=...
REACT_APP_FIREBASE_APP_ID=...
REACT_APP_FIREBASE_MEASUREMENT_ID=...
REACT_APP_API_BASE_URL=http://localhost:5000
```

In Firestore, add security rules so each user can only read/write their own chat
history, and the leaderboard is publicly readable but only self-writable:

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId}/conversations/{conversationId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
    match /leaderboard/{userId} {
      allow read: if true;
      allow write: if request.auth != null && request.auth.uid == userId;
    }
  }
}
```

Then start the dev server:

```bash
npm start
```

### 2. Backend

```bash
cd backend
python -m venv venv
venv\Scripts\activate        # Windows
# source venv/bin/activate   # macOS/Linux
pip install -r requirements.txt
copy .env.example .env       # or: cp .env.example .env
```

Add your Gemini API key to `backend/.env`:

```
GEMINI_API_KEY=your-key-here
```

Then run the API:

```bash
python app.py
```

The frontend expects the backend at `http://localhost:5000` by default (or
`REACT_APP_API_BASE_URL` if you set it).

> **Note on the Gemini free tier:** a free-tier API key is capped around
> 5 requests/minute and 20/day on the current flash model. That's easy to
> exhaust while rehearsing a demo. Either pace out test messages, or enable
> billing on the API key's project — Gemini Flash pricing is a fraction of a
> cent per request, so a full live demo costs well under a dollar.

## Deployment

**Frontend** — `npm run build` produces a static `build/` folder deployable to any
static host. Since the app already uses Firebase, [Firebase
Hosting](https://firebase.google.com/docs/hosting) is a natural fit (`firebase
init hosting`, point it at `build/`, `firebase deploy`); Vercel and Netlify also
work by pointing them at this repo with build command `npm run build` and publish
directory `build`. Either way, set the same `REACT_APP_*` env vars from `.env` in
the host's environment variable settings.

**Backend** — the Flask app is gunicorn-ready via the included `Procfile`
(`web: gunicorn app:app`), which works out of the box on Render, Railway, or any
Heroku-style host. Set `GEMINI_API_KEY` in the host's environment variables, and
set `ALLOWED_ORIGINS` to your deployed frontend's URL (comma-separated if more than
one) so CORS isn't wide open in production. Most hosts inject `PORT` automatically;
`app.py` reads it if present.

## Security Notes

- Never commit real API keys or `.env` files — both are gitignored here.
- The Firebase web config is not a secret by design, but access should still be
  restricted through Firestore security rules (see above), not by hiding the config.
- In production, set `ALLOWED_ORIGINS` on the backend instead of leaving CORS open
  to any origin.
